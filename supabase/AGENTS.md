# Supabase database

## Overview

The database definition: migrations, pgTAP tests, and the local seed. The local stack runs in Docker, so Docker Desktop must be running before any `supabase` command that touches the database. The data model is specced in `docs/specs/0002-data-model/`.

## Key files

| Path | Owns |
|---|---|
| `migrations/` | One SQL file per slice, named `<timestamp>_<name>.sql`. The only way the schema changes. |
| `tests/database/` | pgTAP tests, numbered `NN_<name>.test.sql`, one file per migration slice. `05_merge_readiness.test.sql` checks every foreign key to `games` cascades. |
| `seed.sql` | Local sample community (12 games with tints, five members with a known password, owners, ratings). Loaded by `supabase db reset`. Never run it against the real project. |
| `games-data.sql` | Generated by `pnpm seed:games` from `data/games.json`; idempotent (matches games by normalized name). Safe for the real project. Do not edit by hand. |
| `config.toml` | Local stack settings. |
| `functions/purge-cover-trash/` | Edge Function (Deno) that deletes trashed covers older than 30 days. `purge.ts` holds the logic with no imports, so Vitest tests it (`purge.test.ts`); `index.ts` is the Deno entry. |

## Conventions

- Add a new migration file for every schema change. Never edit a migration that has already been pushed.
- Every new table gets row level security, explicit grants (the default grants are revoked), and a pgTAP test.
- After a schema change, regenerate `src/lib/supabase/database.types.ts`.

## Commands

```bash
supabase test db      # run all pgTAP tests (needs Docker running)
supabase db reset     # rebuild the local database from migrations and seed.sql
supabase db push      # apply new migrations to the linked real project
```

## Gotchas

- **Docker on Windows:** Docker Desktop's CLI lives in `C:\Users\kobe9\AppData\Local\Programs\DockerDesktop\resources\bin`. PowerShell finds it. Git Bash needs it on `PATH`, set in `~/.bash_profile`. If `docker: command not found` appears, run `export PATH="$PATH:/c/Users/kobe9/AppData/Local/Programs/DockerDesktop/resources/bin"`.
- Test files 01 to 04 clear `games` and `auth.users` inside their transaction, so they pass on a seeded database. The rollback restores the seed data.
- `supabase test db` and `supabase status` fail with a Docker error when Docker Desktop is not running. Start it first.
- The `supabase` CLI is linked to the real project (Board-game-community). `db push` changes that project, so check `supabase migration list` first.

## Cover recycle bin purge (spec 0013 amendment)

A replaced or removed cover moves to the private `covers-trash` bucket and gets a `cover_trash` row. A daily `pg_cron` job (`20261124110000_purge_cover_trash_cron.sql`) calls the `purge-cover-trash` Edge Function through `pg_net`; the function deletes files older than 30 days with the Storage API (deleting `storage.objects` rows in SQL would leave the real file behind), then their rows. A failed file keeps its row, so the next run retries it.

One time setup per real project (the migration only schedules the job; secrets never go in migrations):

```bash
supabase functions deploy purge-cover-trash --no-verify-jwt
supabase secrets set PURGE_SECRET=<long random text> PURGE_SERVICE_KEY=<the project secret key>
```

Then, once, in the SQL editor (the second value must equal `PURGE_SECRET`):

```sql
select vault.create_secret('https://<project-ref>.supabase.co', 'project_url');
select vault.create_secret('<same text as PURGE_SECRET>', 'purge_secret');
```

Check a run with `select * from cron.job_run_details order by start_time desc limit 5;` and `select status_code, content from net._http_response order by id desc limit 5;`. Until the secrets exist the job fails harmlessly. Local test: `supabase functions serve purge-cover-trash --env-file <file with PURGE_SECRET=...>`, then POST with an `x-purge-secret` header.
