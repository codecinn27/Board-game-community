# 0001. Stack and architecture for the community board game shelf

**Date**: 2026-10-18
**Status**: Accepted

## Summary

The site is one Next.js app (a React framework that renders pages on the server), hosted free on Vercel under a subdomain of ianhee.com. Supabase provides the database, member sign in (Google or email and password), and storage for game cover images, all from one free account, with a free email service sending sign up and reset emails. This keeps the whole site in one TypeScript codebase you already know how to read, gives Google and chat apps real pages to read, and costs nothing at community scale. Your existing Shinjiru sites are not touched.

## Decision

**Chosen option**: Option 1: Next.js on Vercel with Supabase

One Next.js App Router monolith (a single app, not separate services) in TypeScript, deployed to Vercel Hobby in Singapore, using Supabase (Singapore) for Postgres, Auth, and Storage, with server actions for writes and Resend as the auth email sender.

**Implementation skills**: `supabase` + `supabase-postgres-best-practices` (`supabase/agent-skills`, `.claude/skills/supabase/`, `.claude/skills/supabase-postgres-best-practices/`) · `vercel-react-best-practices` + `vercel-composition-patterns` + `deploy-to-vercel` (`vercel-labs/agent-skills`, `.claude/skills/vercel-react-best-practices/`, `.claude/skills/vercel-composition-patterns/`, `.claude/skills/deploy-to-vercel/`) · `shadcn` (`shadcn-ui/ui`, `.claude/skills/shadcn/`) · `playwright-cli` (`microsoft/playwright-cli`, `.claude/skills/playwright-cli/`)

## Proposed stack

| Layer | Choice | Reason |
|---|---|---|
| Architecture pattern | One Next.js monolith (no separate API service) | One maintainer, under 100 members; one deployable unit is simplest to build, debug, and change. |
| Language | TypeScript (strict mode) | You know React and JavaScript already; one language for screens, server code, and database types. |
| Runtime | Node.js, current LTS line, pinned at scaffold (`engines`, `.nvmrc`) | Vercel's default; scraping and image processing need the Node runtime, not the edge runtime. |
| Framework | Next.js, latest stable major at scaffold time, App Router, version pinned in the lockfile | Server rendered pages for SEO and share previews (feature 20), server code for fetching game data (features 10, 11), all in one project. |
| Rendering | Server Components by default; client components only for interactive parts (rating sliders, forms, language switch) | Fast first load on phones, pages readable by search engines without running JavaScript. |
| Caching of public pages | Public read paths use a Supabase client without cookies so pages can be cached; writes refresh the cache by tag (`revalidateTag`) | Keeps crawlers and bots from burning the Vercel free quota by rendering every page fresh. Signed in parts stay dynamic. |
| Server code | Server actions for form writes; route handlers only where a URL is needed (keep alive, health check, link auto fill if needed) | Fewest moving parts; no hand written REST layer to keep in sync. |
| Request middleware | One `proxy.ts` (Next.js middleware) that chains next-intl locale handling and the `@supabase/ssr` session refresh | Both need to run on every request; one file keeps their order explicit. The locale URL pattern itself is decided in the two languages spec. |
| Primary DB | Supabase Postgres (free plan), region Singapore (`ap-southeast-1`) | Relational data (games, owners, ratings, comments) fits Postgres; closest region to Malaysia. |
| Postgres extensions | `pg_trgm` (trigram index, matches small chunks of text) | Postgres word based search cannot split Chinese text; trigram `ilike` search works for Chinese and English names. |
| Database access | `@supabase/supabase-js` with `@supabase/ssr` for cookies; TypeScript types generated by the Supabase CLI | One way to touch the database, the same client that carries the signed in member into row level security. |
| Privileged access | One `createAdminClient()` module marked `server-only`, the only place the secret key is used; admin actions check the member's role first; multi step admin changes (merging games) run as Postgres functions in one transaction | The secret key bypasses every security rule, so it must live in one guarded place. |
| Migrations | Supabase CLI SQL migrations in `supabase/migrations/`, committed to git; applied to production by you with `supabase link` + `supabase db push` from your PC; migrations go out before the code that needs them | Simple and visible for one maintainer; automate in CI later if it becomes a chore. |
| Access control | Postgres row level security (RLS, database rules deciding which rows each member may read or change) on every table | Public read, member write, owner only edits enforced in the database itself, not just in the UI. |
| Auth | Supabase Auth: Google OAuth + email and password, email confirmation on | Built into the platform already chosen; one tap Google sign in on phones, email for anyone without Google. |
| Auth session checks | Session refreshed in `proxy.ts`; server code checks the member with `getClaims()` (or `getUser()`), never `getSession()` | `getSession()` trusts the cookie without verifying it, so it must not decide permissions. |
| Bot protection | Cloudflare Turnstile captcha on sign up and sign in, through Supabase Auth's captcha setting | Free, invisible to most people, stops automated fake accounts on a public site. |
| Transactional email | Resend (free tier) as custom SMTP for Supabase Auth, sending from an `ianhee.com` address with SPF and DKIM records | Supabase's built in sender only reaches your own team addresses at about 2 emails per hour, so member sign up would fail without this. |
| File storage | Supabase Storage, one public bucket `covers`; only the server writes to it | Covers are copied in when a game is added, so pages never break if a source site changes or blocks hotlinking. |
| Images | Covers resized once when a game is added (`sharp`, to WebP, two sizes), then served straight from Supabase Storage with `next/image` set to `unoptimized` | Avoids Vercel's small free image optimization quota; files are already small for mobile data. Size and type limits set in the online lookup spec. |
| Styling | Tailwind CSS (current major) + shadcn/ui | Quick mobile first layouts plus accessible components (dialogs, sliders, forms) the project owns and can restyle in the design system spec. |
| Forms & validation | Zod schemas shared by browser and server, React Hook Form on the client | One set of rules checks input instantly on the phone and again on the server. |
| Translations | next-intl | Standard i18n library for the App Router; supports server rendered, language aware pages. |
| Search | Postgres `ilike` backed by a `pg_trgm` index | Hundreds to a few thousand games need no separate search engine. Details in the search & filters spec. |
| Background jobs | Vercel Cron, one daily job | Only job today is the keep alive ping; no queue needed. |
| Keep alive | Daily Vercel Cron call to `/api/keepalive`, which checks `CRON_SECRET` and runs one tiny read on Supabase | Stops the free Supabase project from pausing after 7 quiet days. |
| Uptime | UptimeRobot (free) pinging `/api/health` every few minutes, emailing you on failure | Vercel's free logs keep little history, so you would not otherwise see an outage; also a second keep alive. |
| Hosting | Vercel Hobby (free), functions in Singapore (`sin1`), custom domain `boardgame.ianhee.com` (final name yours) via a CNAME record at Shinjiru pointing to Vercel | Built for Next.js, deploys every git push, preview link per branch, free for non commercial use, HTTPS included. |
| Source control & CI | GitHub, private repo, connected to Vercel; GitHub Actions for checks | Push to deploy; lint, typecheck, and tests run on every pull request (exact checks set by `/audit`). |
| Package manager | pnpm, version pinned via `packageManager` in `package.json`; lockfile committed | Fast, strict about dependencies, same version everywhere. |
| Local development | Supabase local stack via Docker Desktop (`supabase start`), Next.js dev server | Safe place to try migrations and seed data before production. |
| Testing | Vitest (unit) + Playwright (browser flows, including a phone sized viewport); CI starts local Supabase, seeds an email test user, and mocks outside game sources | Matches the Beta workflow; tests never depend on real Google sign in or live outside sites. |
| Observability | Vercel runtime logs, structured `console` logs from server code, plus the uptime check | Enough for a small community site; add an error tracker only when problems become hard to trace. |
| Backups | Weekly database export you run yourself (`supabase db dump`) kept outside Supabase | Free plan backups are not something you can download and restore on your own. |
| Privacy | No third party trackers; the privacy note lists Supabase, Vercel, and Resend as the services that handle member data | Only email addresses and names are stored; nothing else needs consent banners. |

**Environments**

| Environment | App | Database and auth |
|---|---|---|
| Local | `pnpm dev` | Supabase local (Docker); values printed by `supabase start` |
| Preview | Vercel preview deployment per branch | Second free Supabase project as **staging** (Singapore); sign in redirect list allows Vercel preview URLs |
| Production | Vercel production, `boardgame.ianhee.com` | Supabase production project (Singapore) |

**Configuration required** (where each value comes from)

| Variable | Purpose | Local | Preview | Production |
|---|---|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase project URL | `supabase start` output | staging project settings | production project settings |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Publishable key (`sb_publishable_…`), safe in the browser because RLS protects data; replaces the legacy `anon` key | `supabase start` output | staging | production |
| `SUPABASE_SECRET_KEY` | Secret key (`sb_secret_…`, replaces `service_role`), bypasses RLS; used only in `createAdminClient()` | `supabase start` output | staging secret key | production secret key (set for the Production environment only) |
| `CRON_SECRET` | Lets only Vercel Cron call `/api/keepalive` | any value | not needed | generated random string |
| `NEXT_PUBLIC_SITE_URL` | Base URL for sign in redirects, sitemap, share previews | `http://localhost:3000` | Vercel preview URL (`VERCEL_URL`) | `https://boardgame.ianhee.com` |

Set outside the app (dashboards, not env vars):
- **Supabase Auth, per project**: Site URL; redirect URL allowlist (localhost, the production domain, and the Vercel preview URL pattern for staging); Google provider client ID and secret; Turnstile secret; custom SMTP host, user, and password from Resend; email confirmation on.
- **Google Cloud**: OAuth client with the Supabase callback URLs of both projects; consent screen **published** (in Testing mode only 100 test users can sign in and logins expire after 7 days).
- **Resend**: verified sending domain `ianhee.com` (SPF and DKIM DNS records added at Shinjiru).
- **Cloudflare Turnstile**: site key (in the sign up form) and secret (in Supabase).
- **Vercel**: function region `sin1`; env vars per environment as above.
- **Shinjiru DNS**: CNAME for the subdomain to Vercel, plus Resend's SPF and DKIM records.
- **GitHub**: Actions secrets only if migrations are automated later (`SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, project ref).

Secrets live only in Vercel, Supabase, and GitHub settings. A `.env.example` listing every variable (no values) is committed; `.env.local` is git ignored.

**Directory layout (high level, details set by `/audit`)**
- `src/app/` routes and pages (App Router); `src/proxy.ts` request middleware
- `src/components/` shared UI, `src/components/ui/` shadcn/ui components
- `src/lib/supabase/` server, browser, public (no cookies), and admin (`server-only`) Supabase clients
- `src/features/<feature>/` actions, schemas, and components per feature
- `messages/` translation files (`en.json`, `zh.json`)
- `supabase/` migrations, seed, local config
- `tests/` Playwright tests; unit tests next to the code they test

## Consequences

**Positive**:
- Zero hosting cost at community scale; your existing Shinjiru sites are untouched.
- One TypeScript codebase and one platform for data, sign in, and files, so few things can break between them.
- Public pages are server rendered and cached, so SEO and share previews (feature 20) need no extra infrastructure and bots barely touch the free quota.
- Security rules live in the database, so a mistake in a page cannot leak or overwrite another member's data.

**Negative / tradeoffs**:
- Five free accounts to look after (Vercel, Supabase, Resend, Cloudflare Turnstile, UptimeRobot), each with its own limits. Vercel Hobby is non commercial only; Supabase free has 500 MB database, 1 GB storage, and two projects (both used: production and staging).
- Vercel functions are serverless (they start fresh per request): a slow source site during scraping hits a time limit, so lookups must fail fast and fall back to manual entry.
- Row level security is powerful but easy to get wrong; every table needs policies and tests, and the secret key must never leave `createAdminClient()`.
- Production migrations are a manual step you must remember before deploying code that depends on them.
- Backups depend on you running the weekly export.
- Local development needs Docker Desktop on Windows.

**Neutral**:
- New patterns to learn if you haven't used them: server actions, Server vs Client Components, RLS policies, Supabase CLI migrations.
- The scaffold installs only what the first slice needs (Next.js, TypeScript, Tailwind, shadcn/ui, Supabase clients, next-intl); each later feature adds its own libraries when built (for example `sharp` with online lookup).
- Exact versions are recorded at scaffold time (lockfile, `packageManager`, `.nvmrc`) and noted in `AGENTS.md` by `/audit`.
