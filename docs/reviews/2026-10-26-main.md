## Minor
### 🟡 Comment says service_role keeps select on the log, but nothing grants it, `supabase/migrations/20261025090000_admin_tools.sql:188-191`
**Problem**: The comment says "service_role gets select only, too", but the code runs `revoke all ... from anon, authenticated, service_role` and then grants `select` back only to `authenticated`. So `service_role` cannot read `admin_actions` at all. The spec only requires revoking update, delete, and truncate from service_role.
**Why it matters**: A future server-side job or admin script that uses the secret key will get `42501` on the log. The comment will mislead whoever debugs it.
**Suggested fix**: The migration is already pushed, so do not edit it. Pick the intended behaviour. If service_role should read the log, add a small migration with `grant select on public.admin_actions to service_role`. If it should not, record that in the spec or in supabase/AGENTS.md so the wrong comment doesn't spread. Add a pgTAP assertion either way.

### 🟡 `save_top_picks` can raise a unique violation on a concurrent double submit, `supabase/migrations/20261024120000_top_picks_wishlist.sql:85-89`
**Problem**: The function deletes and then inserts. Suppose two calls for the same member overlap, for example a double click or two tabs. Under read committed, the second call's DELETE does not see the rows the first call inserted. Its INSERT then fails with `23505` on the `(member_id, position)` or `(member_id, game_id)` key.
**Why it matters**: The user sees an unexpected error instead of "last write wins". The data stays consistent.
**Suggested fix**: In a new migration, serialize per member before the delete, for example `perform pg_advisory_xact_lock(hashtextextended((select auth.uid())::text, 0))`. Alternatively, lock the caller's profile row with `select ... for update`. The app could also map `23505` to a retry.

### 🟡 Admin game delete in test 01 asserts only that no error was raised, `supabase/tests/database/01_foundation_thread.test.sql:201-202`
**Problem**: `lives_ok` passes even if RLS silently deletes zero rows. The same file already has `tests.affected(...)`, which checks the row count.
**Why it matters**: The assertion would still pass if the admin delete policy broke. Test 04 does cover the real delete, so this is weak duplication rather than a hole.
**Suggested fix**: Use `is(tests.affected($$ delete ... $$), 1::bigint, ...)`.

### 🟡 Avatar storage tests are missing two cases, `supabase/tests/database/04_admin_tools.test.sql:193-222`
**Problem**: The tests cover member insert, insert into another member's folder, insert into covers, and own update and select. Two of the four policies have untested paths: there is no test for the delete policy (own folder versus another member's folder), and none for a disabled member's update or delete. The `allowed_mime_types` setting is not asserted either.
**Why it matters**: These policies are security-relevant, and test coverage is configured for this project.
**Suggested fix**: Add a delete test for the member's own avatar file and one for another member's file. Add a disabled-member update test and a check on `allowed_mime_types`.

## Nits

- ⚪ `supabase/migrations/20261024120000_top_picks_wishlist.sql:77-89`: a multi-dimensional array passes validation and gets flattened. It is harmless; checking `array_ndims(game_ids) <= 1` would make the contract exact.
- ⚪ `supabase/migrations/20261023164946_foundation_thread.sql:209` (context): when an account is deleted, the `added_by` set-null cascade also bumps `updated_at` on that member's games through `set_updated_at`. This is probably fine, but it is a side effect worth knowing about.
- ⚪ The remote security advisor warns that authenticated users can execute the SECURITY DEFINER function `admin_set_member_status`. This is intended, since the function checks `is_admin()` first. Note it as accepted in supabase/AGENTS.md so later audits don't chase it.
- ⚪ `docs/scope/scope.md`: "Verify it" and "Test it" are ticked, but `docs/reviews/` had no verify report before this review. Make sure that evidence exists.

## Strengths
- The log trigger design is solid. It finds cascaded comment deletes by checking whether the game row still exists, because `pg_trigger_depth()` cannot detect FK cascades, and the comment in the code explains why. It skips logging when an admin edits their own row, it never logs the deleted comment text, and the AC-13 tests check that each action writes exactly one row.
- `05_merge_readiness.test.sql` guards AC-15 well. A new table pointing at `games` without a cascading `game_id` key fails the build on purpose.
- Grants follow the "grants first" rule: column-level insert grants, only `select` on the log, and `execute` revoked from `anon`/`public` on both RPCs. Every function sets `search_path = ''`.
